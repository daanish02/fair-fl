# Research Proposal: An Agentic Runtime Governor for Trajectory-Aware Group Fairness Enforcement in Federated Learning

## 1. Problem

Federated Learning (FL) systems that enforce group fairness (e.g., Equal Opportunity Difference, EOD, or Statistical Parity Difference, SPD) rely on mechanisms whose behavior is fixed before training starts and re-evaluated only against the current round's data:

- **FairFed** (AAAI'23) recomputes each client's fairness gap Δ_k^t fresh every round and reweights aggregation using a single **static scalar budget β**, set once, before training.
- **FedAA** (AAAI'25) filters client updates using a **static percentage threshold M%**, and the authors explicitly avoid making M% adaptive because a naive learned policy is trivially gamed by colluding malicious clients (Module 3 of our notes on that paper).
- **pFedFair** (2025) personalizes fairness constraints via Moreau envelopes, but the balance parameters λ, η, γ are likewise **fixed offline hyperparameters**.

All three—and every other fairness mechanism across the 20 papers reviewed for this dissertation—share the same structural limitation: they evaluate fairness as an **instantaneous snapshot** at round t, using only that round's state. *Remembering to Be Fair* (Alamdari et al., ICML'24) proves formally that fairness in any sequential decision process is properly a property of the **full historical trace** τ_t = (s_1, a_1, ..., s_t), not the current state alone — a policy can look fair at every checkpoint while systematically favoring one client early and "correcting" only late, and instantaneous metrics cannot detect this. That paper calls the correctly-posed problem **non-Markovian** (the fairness judgment cannot be computed from the current state alone) and solves it by folding history into a bounded memory variable so a standard learner can still act on it.

**No FL fairness paper in this literature applies that framework.** Every existing mechanism also responds identically to every kind of fairness drift — a formula cannot distinguish a client's EOD drifting because of genuine non-stationary data shift (which should be tolerated and reweighted) from drift caused by a poisoning attack or a spurious one-round blip (which should be flagged or ignored). Static formulas are diagnosis-blind by construction. This isn't a one-paper gap: FedAA routes its weighting decision through a trained RL policy instead of a formula, but the policy's reward is still computed from a single round's validation accuracy, so it inherits the same blind spot as FairFed's formula; q-FFL's loss-tilting exponent and Agnostic FL's min-max both react to the current round's loss alone; pFedFair's personalization split is decided once, structurally, with no per-round trigger at all. None of the five mechanisms surveyed can distinguish a sustained shift from a transient anomaly, because none of them look past the current round.

### 1.1 Which Fairness, Whose Harm

"Minority" means two different things across this literature, and they carry different stakes. One is a **demographic subgroup within the aggregated model's predictions** (race, gender, age — FairFed's, pFedFair's, and the Bias-in-FL survey's usage), where getting it wrong is a person-level harm: a patient, a loan applicant, a defendant. The other is an **underrepresented client** (a hospital, sensor, or bank branch with less data or an atypical local distribution — the TILES wearable-sensor case study in the FairFed note is a clean example), where getting it wrong is a client-level harm that may or may not translate into a harm for a person on the other end, depending entirely on what that client represents. The Bias-in-FL survey's own healthcare example collapses the two ("small rural clinics with sparse data receive suboptimal models, exacerbating healthcare inequalities") precisely because the client there is a proxy for an underserved patient population; its autonomous-vehicle and sensor examples do not carry the same stakes. This dissertation evaluates primarily on **person-level demographic fairness** (Adult, COMPAS — client-level harm and demographic harm coincide in these datasets), matching FairFed's and pFedFair's own evaluation choice, rather than treating device/sensor-level underrepresentation as an equivalent-stakes problem.

## 2. Research Question

Can a runtime agent, reasoning over each client's **fairness trajectory** (not just its current-round metric) and available client metadata, diagnose *why* a client's group-fairness gap is drifting and select an appropriate response — outperforming static, instantaneous-snapshot fairness mechanisms (FairFed, FedAA) under non-stationary client data drift, without requiring a trained/learned policy?

## 3. Proposed Contribution

**System: the Server Governor Agent.** A single agent, co-located with the FL server, that replaces the static reweighting step in a FairFed-style pipeline. Each round it:

1. **Maintains state**: a per-client trajectory buffer of EOD/SPD values over the last *k* rounds (a bounded memory variable, not the full unbounded history — this keeps the "non-Markovian" fairness signal tractable, following the memory-augmentation approach in *Remembering to Be Fair*).
2. **Diagnoses**: given a client's trajectory shape (steady drift vs. spike-and-revert vs. sudden step change) plus lightweight client metadata (round-over-round data volume change, participation history), a **deterministic statistical decision procedure** (trend/slope tests, volatility bounds, cross-client comparison — see Section 5.2) classifies the likely cause first: *sustained non-IID distribution shift*, *transient noise*, or *anomalous/suspicious change*. Only when the statistical procedure cannot confidently classify a case does it get **escalated to an LLM reasoning step** as a fallback. This math-first, LLM-as-fallback split is a deliberate design decision (not left open — see Section 5.2), chosen specifically to minimize hallucination risk and keep the majority of decisions fully explainable, with LLM reasoning reserved for genuinely ambiguous edge cases a fixed statistical rule can't resolve.
3. **Responds**: based on the diagnosis, selects one of a small, fixed action set — increase/decrease that client's aggregation weight (a **per-client, time-varying β_k(t)**, generalizing FairFed's single global static β), leave the client's weight unchanged, or flag the client for exclusion from the round.

This is deliberately **not** a learned/RL policy (that is explicitly out of scope for this MSc phase — see Section 5.1 of the dissertation handoff, and Section 5 below). The agent's contribution is the diagnose-then-respond reasoning loop itself: a static formula reacts identically to every drift regardless of cause, by construction; separating causes and choosing among discrete responses is the part no existing mechanism in this literature does.

### 3.1 Worked Example: The Same Numbers, Two Different Causes

Consider one client, B, with the same six-round EOD trajectory magnitude in two different underlying situations:

- **Scenario 1 (genuine drift)**: `-0.05, -0.06, -0.05, -0.18, -0.19, -0.20` — B's local population shifted starting round 4 (e.g. a new district began contributing data), B's data volume jumped accordingly (500 → 1,400 samples), and similarly-situated peer clients show the same worsening trend starting the same round.
- **Scenario 2 (transient anomaly, already recovering)**: `-0.05, -0.06, -0.18, -0.14, -0.09, -0.05` — a single corrupted update at round 4, since corrected, with the gap visibly reverting; B's data volume stayed flat the whole time; no peer client shows a comparable shift.

A snapshot-only mechanism (FairFed's Δ_k^t, FedAA's per-round reward, q-FFL's per-round loss exponent) sees a large current-round gap in both cases and reacts the same way in both — typically, suppressing B's weight. The diagnosis step instead runs three checks before deciding anything: **(1) trend shape** — is this a sustained step-change or a spike that's already reverting; **(2) metadata correlation** — did B's data volume change at the same time the gap moved; **(3) peer correlation** — did similarly-situated clients shift the same way at the same time. Scenario 1 answers yes/yes/yes, and is classified *sustained legitimate shift* — the correct response is to **increase** B's weight, so the model actually adapts to the new population instead of being punished for representing it. Scenario 2 answers no/no/no, and is classified *transient, self-correcting* — the correct response is to **leave B's weight unchanged** and let it continue recovering. The two scenarios produce opposite actions from the same current-round gap size, which no mechanism reviewed in this literature can do, because none of them retain the trajectory, metadata deltas, or peer comparison needed to tell the two cases apart.

### 3.2 Why an Agent, and Not Just an If/Else Tree

The three checks above are, by themselves, plain deterministic code (a slope test, a rolling-variance bound, a correlation check) — no reasoning or LLM involvement is needed to compute them, and claiming otherwise would be dressing up ordinary statistics as AI. The open question this dissertation actually tests is narrower: what happens when the three checks **disagree** — e.g. trend looks sustained, but no peer corroborates it and no metadata change explains it. A hand-built decision table would need every such combination anticipated in advance, and would still be surprised by a combination nobody thought to encode; an LLM reasoning step, given the same trajectory and metadata as context, can weigh a novel combination using the same kind of contextual judgment a human FL engineer would apply, without that combination having been enumerated ahead of time.

This yields a falsifiable design claim, stated plainly rather than assumed: **if the feasibility spike (Section 5.3) shows the three deterministic checks resolve every case encountered without hitting a genuinely ambiguous combination, the honest conclusion is that this problem did not require an LLM at all**, and the dissertation's contribution would narrow to "trajectory-and-metadata-aware reweighting via deterministic statistics" — still a valid, publishable result, just a smaller one than a governing agent. The dissertation commits to testing for this condition rather than assuming the agent framing is necessary.

### 3.3 Architecture: Tool-Based, Extensible by Design

The agent's action set (Section 3, step 3) is implemented as a small set of discrete, independently callable **tools** — e.g. `get_client_trajectory(client_id)`, `adjust_weight(client_id, delta)`, `flag_client(client_id, reason)` — rather than as inline branching logic inside one monolithic reasoning function. The diagnosis step (step 2) selects which tool(s) to invoke based on its classification, the same pattern used by the ToolAgent proof-of-concept in the Agentic-FL note.

This is an implementation choice, not an evaluated claim: **only the fairness-diagnosis tool set is built and evaluated in this dissertation.** But building the agent against a generic tool interface from the start — rather than hardcoding fairness-specific logic into the agent's core loop — means the same runtime (trajectory buffer, diagnose-then-respond loop, LLM reasoning step) could later host additional tools for other FL concerns named across this literature but out of scope here, e.g. Byzantine-robustness filtering (RoFL, FedAA's M% threshold) or dynamic privacy-budget tuning (the R-DPCFL note's ε_select). This extensibility is named explicitly as **future work** (Section 8 of the dissertation handoff's open-items list is the natural place to track it going forward) — it is not something this dissertation builds, tests, or claims as a contribution, precisely to keep the evaluated scope narrow and defensible per Section 5.1 below.

### 3.4 Baselines and Evaluation

- **Baselines**: FedAvg (no fairness mechanism), FairFed (static global β), q-FedAvg or FedAA-style static threshold filtering.
- **Fairness metrics**: per-client and global EOD/SPD, tracked round-over-round (not just final-round).
- **Drift scenarios to construct**: (a) sustained non-IID shift injected mid-training on a subset of clients, (b) a transient one-round anomaly on an otherwise well-behaved client, (c) a genuinely malicious client with adversarially manipulated local metrics, to test whether the diagnosis step avoids being fooled the way FairFed's honest-reporting assumption is (Module 5, FairFed note). Scenario (c) is evaluated only against the fairness-diagnosis tool set's behavior (does it correctly flag rather than reweight); it is not a claim about Byzantine-robustness as a solved problem — that remains future work per Section 3.3.
- **Utility cost**: global model accuracy under each scenario, to confirm fairness gains aren't bought by destroying top-line performance — matching the utility-tradeoff framing FairFed and FedAA both report.

## 5. Feasibility

### 5.1 Scope constraints (deliberate, not limitations)

- **Rule-based agent, not RL.** The agent's diagnosis step is an LLM call (or a small decision-procedure the LLM output is checked against) over a compact per-client feature vector — trajectory shape summary statistics, participation/data-volume deltas — not a trained policy network. This avoids the RL sample-complexity and reward-design risk that FedAA's authors flag as a reason they kept M% static, and matches the one-semester timeline.
- **Server-only, single-agent.** No client-side "Guardian Agent" tier in this phase (that two-tier design recurs across the notes' dissertation-bridge sections but roughly doubles implementation and evaluation surface). Clients remain standard FL clients; only the server-side reweighting step is replaced.
- **Bounded memory, not unbounded history.** The trajectory buffer is a fixed sliding window (e.g., last 10 rounds), not the full training history — keeps the state space small and avoids the "infinite state expansion for non-regular status functions" failure mode *Remembering to Be Fair* itself flags as an open limitation (Module 6 of that note).
- **Client selection stays standard (uniform random), untouched.** Only aggregation weighting is replaced. This is deliberate, not an oversight: routing the same trajectory history into *both* selection and weighting risks a client the diagnosis is merely uncertain about — including a genuine minority client with naturally noisier statistics — simply not being picked at all, which forecloses the weighting fix downstream entirely (an update never collected can't be reweighted). This is exactly the "Selection Exclusion" bias the Bias-in-FL survey names (Chunk 1), and exactly why FairFed, FedAA, and pFedFair all keep selection untouched and intervene only at aggregation. Compared against Oort/Power-of-Choice-style selection (optimizes for loss/speed, actively excludes slow or low-capability clients) and FedCS-style latency filtering (same exclusion risk), uniform random is the only option of the three that doesn't inject a second, selection-side bias the aggregation-side mechanism would then have to separately correct for. Concentrating the entire fairness correction in one mechanism (aggregation weighting) also keeps the evaluation's causal story clean — any fairness gain measured has exactly one explanation — and is less implementation and evaluation surface than building and untangling two separate correction mechanisms. A history-guided *selection-priority boost* (never exclusion, only ensuring drifting clients get selected often enough to keep diagnosing them) is a plausible future extension, tracked alongside the Section 3.3 extensibility list rather than built this semester.
- **Selection-recency as a weighting signal is a separate, held-out hypothesis, not part of this dissertation's mechanism.** A distinct idea considered during design: boost a client's aggregation weight based on how long it's been since that client was last selected (a participation-recency signal), independent of its fairness trajectory. This is deliberately **not** folded into the core mechanism, because it answers a different question than the one this dissertation tests — "has this client been selected rarely" is not evidence of "this client's fairness metrics are drifting for a legitimate reason," and a client selected infrequently may already be well-represented in the model if its local distribution resembles the majority. Mixing a participation signal into a fairness-diagnosis mechanism would make any measured effect impossible to attribute to one cause or the other, undermining exactly the single-variable causal story this proposal is built around (Section 5.1, "Client selection stays standard"). If pursued at all, it should be tested as its own, separately-evaluated hypothesis — not merged into the trajectory/metadata signal already driving β_k(t).

### 5.2 Implementation plan

- **FL substrate**: Flower (already the framework used in the Agentic-FL and Helmsman papers' proofs-of-concept, so tooling precedent exists in this exact literature) with a custom server-side `Strategy` that intercepts the standard weighted-aggregation step.
- **Datasets**: Adult and COMPAS under Dirichlet non-IID partitioning (α sweep), matching FairFed's and pFedFair's own evaluation setup — this lets results be compared directly against numbers already reported in those papers rather than requiring a from-scratch baseline reproduction.
- **Agent reasoning**: a small number of LLM calls per round (one per flagged client, not one per client per round, to control cost) — following the OpenFedLLM/ToolAgent cost-scaling lesson from the Agentic-FL note (raw-context approaches don't scale with client count; targeted, filtered queries do).
- **Diagnosis logic (committed design, math-first)**: the primary classifier is a deterministic statistical pipeline — trend/slope test on the trajectory window, a volatility/variance bound to catch spike-and-revert cases, and a cross-client comparison (is this client's shift shared by similarly-situated clients, which points to genuine distribution shift, or is it an outlier against its peers, which points to anomaly/attack). This pipeline handles the classification whenever its output is confident/unambiguous by an explicit, pre-defined margin. **The LLM is invoked only as a fallback**, for the residual cases where the statistical pipeline's confidence falls below that margin (e.g. conflicting signals, insufficient trajectory history, or a shape the fixed rules don't cleanly cover) — not as a parallel or primary decision-maker. This ordering is chosen specifically to (a) minimize hallucination risk by keeping the LLM off the critical path for the majority of rounds, and (b) keep the system's decisions explainable by default, with LLM involvement itself logged as a flag on any decision it touches.
- **Tool interface**: define the action set (Section 3.3) as a small, documented function-call schema (name, arguments, return type) from the start, even though only the fairness tools are implemented this semester — this is a few hours of upfront interface design, not a scope increase, and is what makes the extensibility claim in Section 3.3/4 honest rather than aspirational.

### 5.3 Main technical risk and de-risking plan

- **Risk**: the diagnosis step must reliably distinguish "legitimate drift" from "adversarial/anomalous" using only aggregate metrics and metadata the server can see (no raw client data) — this is the same information-scarcity problem FairFed's own limitations section names (Module 5: FairFed assumes honest client reporting).
- **De-risk plan**: before committing to the full multi-scenario evaluation, run a small spike — two clients, one with injected genuine non-IID drift and one with an injected single-round anomaly, over ~20 rounds — and confirm the diagnosis step can tell them apart using only the trajectory + metadata signal, before scaling to the full client population and adversarial scenario.
- **Fallback if diagnosis proves unreliable**: degrade gracefully to a non-Markovian-but-non-diagnostic version (dynamically adjust β_k(t) from trajectory shape alone, no cause classification) — still a genuine improvement over FairFed's static global β, and still defensible as a standalone contribution if the full diagnose-then-respond loop doesn't hold up empirically.

## 8. Design Decision Log

**Math-first, LLM-as-fallback (decided 2026-09-21).** Considered a purer "LLM reasons over every case" design, closer to the notes' original Agentic-FL framing and possibly reading as more novel to a PhD supervisor audience — rejected in favor of the statistical-pipeline-first design in Sections 3/5.2. Rationale: minimizing LLM involvement on the critical path reduces hallucination risk and keeps the large majority of the agent's decisions fully explainable by a fixed, inspectable procedure, with the LLM reserved for genuinely ambiguous cases the statistics can't resolve. This also makes the system easier to evaluate rigorously (deterministic behavior is reproducible; LLM-touched decisions are a smaller, explicitly logged subset that can be audited separately) — a better fit for a one-semester dissertation than a design whose behavior is harder to pin down for evaluation purposes.

**Trajectory history drives weighting only, never selection (decided 2026-09-21).** Considered feeding the same trajectory/metadata signal into client selection as well as aggregation weighting (e.g. to give drifting or minority clients a selection advantage) — rejected for the core evaluated system. Rationale: any selection-side use of a signal the agent is still uncertain about risks excluding exactly the clients the weighting mechanism exists to protect, and an update that's never selected can never be reweighted. Keeping selection uniform-random and untouched also keeps the evaluation's causal story to one variable (aggregation weighting), avoiding the confound and doubled implementation/evaluation cost of two overlapping correction mechanisms. A non-exclusionary selection-priority boost (ensuring drifting clients are sampled often enough to keep diagnosing them, never used to drop a client) remains a plausible, separately-scoped future extension — see Section 5.1.
