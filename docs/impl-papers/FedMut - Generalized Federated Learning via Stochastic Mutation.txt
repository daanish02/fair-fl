2. PROBLEM SETUP
================================================================================

Standard FedAvg-style FL dispatches the SAME global model to every client each
round. Under non-IID client data, this tends to drive the global model into a
sharp (poorly-generalizing) region of the loss landscape, because local
optimization directions diverge ("gradient divergence") and FedAvg's coarse
averaging can't resolve conflicting local updates. The paper's core empirical
intuition (illustrated via loss-landscape plots, Fig. 1): different clients'
loss landscapes, while not identical, tend to have flat optimal regions that
overlap more than their sharp optimal regions do. So guiding training toward a
flat region is more likely to generalize well across clients simultaneously.

FedMut's idea: instead of sending every activated client the same global
model, the server generates K different "mutated" versions of the global
model (random perturbations along the model's own gradient directions,
layer-wise, with sign +1/-1) and dispatches one distinct mutated model to each
activated client for local training. If the global model's neighborhood lies
within a single flat basin, all mutated models stay in that basin and their
locally-trained versions, once re-aggregated, pull the global model toward the
center of that flat area. If the global model is in a sharp area, mutation
pushes some clients' starting points out of the sharp region entirely, which
drags the aggregated model toward a flatter region over successive rounds.
Because mutation only touches the aggregated global model (not individual
client uploads), FedMut remains compatible with secure aggregation and needs
no extra data or communication.

================================================================================
3. ALGORITHM
================================================================================

--- Per-round pipeline (Fig. 3, prose "Overview" section) ---
Six steps per FL round:
1. Model Dispatching: server sends K distinct mutated global models to K
   activated clients (one mutated model per client).
2. Local Training: each activated client trains its received mutated model on
   local data.
3. Model Uploading: clients upload trained local models to server.
4. Model Aggregation: server aggregates the K uploaded local models into a new
   global model (standard FedAvg-style aggregation step).
5. Model Mutation: server mutates the newly aggregated global model, using the
   gradient (= difference vs the PREVIOUS round's global model), to produce K
   new mutated models for the NEXT round's dispatch.
6. Model Updating: server replaces the stored "old global model" with the
   current round's aggregated global model (for computing next round's
   gradient).

--- Algorithm 1 (FedMut top-level loop), as printed ---
Input: round (# training rounds), C (set of involved clients), K (# activated
clients per round).
Output: w_glb (trained global model).

1: w_glb^0 <- w_0                          // initialize global model
2: w_1^mut, ..., w_K^mut <- w_glb^0        // initialize mutated models (all = initial global model, since round 1 has no gradient yet)
3: for r = 1, ..., round do
4:   L_c <- Randomly select K clients from C
     /* parallel for block */
5:   for i = 1, ..., K do
6:     w_i^r <- LocalTraining(w_i^mut, L_c[i])
7:   end for
8:   w_glb^r <- ModelAggregation(w_1^r, ..., w_K^r)
9:   [w_1^mut, ..., w_K^mut] <- ModelMutation(w_glb^r, w_glb^(r-1), K)
10: end for
11: return w_glb^r

(Line 2 note from prose: in round 1 the server has no gradient to mutate from,
so all K "mutated" models dispatched in round 1 are literally just the
initial global model — mutation only kicks in from round 2 onward, once a
gradient w_glb^r - w_glb^(r-1) exists.)

--- Core mutation equation (Eq. 2) ---
Let w_glb = {layer_1, ..., layer_L} (L layers) and g_glb = {lg_1, ..., lg_L}
be the gradient of w_glb (= weight change of the global model relative to the
OLD global model from the previous round, i.e. g_glb = w_glb - w_glb_old).

For the i-th mutated model, first draw a per-layer mutation sign list
L_mut^i = [v_1^i, ..., v_L^i], v_j^i in {-1, 1}. Then:

    w_mut^i = { layer_1 + alpha * v_1^i * lg_1,
                layer_2 + alpha * v_2^i * lg_2,
                ...,
                layer_L + alpha * v_L^i * lg_L }                    (Eq. 2)

alpha is a hyperparameter controlling the distance of each mutated model from
the global model — a higher alpha means a larger neighborhood / more
aggressive mutation, which can guide the model toward a flatter area, but if
alpha is too large the neighborhood may exceed the width of any flat basin
and training fails to converge (confirmed empirically in ablations, see
Section 4 below).

--- Uniform-mean / zero-sum sign constraint (Eq. 3, Eq. 4) ---
To keep the mutated models evenly distributed around the global model (so
that re-aggregating them reconstructs the global model on average), the paper
imposes:

    w_glb = (1/K) * sum_{i=1}^{K} w_mut^i                                (Eq. 3)

which, since alpha and lg_j are shared across all K mutated models for a
given layer j, reduces to requiring the signs to sum to zero per layer:

    sum_{i=1}^{K} v_j^i = 0        for every layer j                      (Eq. 4)

In other words it is a BALANCED/uniform-mean construction by design — exactly
half of the K sign values for each layer are +1 and half are -1 (this is a
structural property of how the mutation signs are drawn, not a separate
"weighted vs uniform aggregation option" choice the user can toggle; see note
below). If K is odd, one slot is reserved: w_mut^K is simply set to w_glb
unmutated (w_mut^K = w_glb when K mod 2 = 1), and the sign-balancing is done
over the remaining K-1 (even) slots.

NOTE ON "weighted vs uniform mean aggregation option": the paper's Eq. 3/Eq.4
balance condition concerns the MUTATION step (ensuring mutated models average
back to the global model), not the ModelAggregation step in Algorithm 1 line
8. The paper does NOT explicitly discuss weighted-vs-uniform options for the
Model Aggregation step (step 4 / line 8) in the main text — it simply says
"the cloud server aggregates these local models to generate a new global
model," analogous to FedAvg, without specifying weighting by local dataset
size vs uniform/unweighted averaging. The archive config's claim of "uniform
(unweighted) mean aggregation" is therefore NOT something this paper's text
explicitly confirms or denies for the FedAvg-style aggregation step — it must
be a choice made in the official FedMut code (not shown in this PDF). Flagging
this as unverified-from-paper-text.

--- Algorithm 2 (ModelMutation), as printed ---
Input: w_glb (global model), w_glb' (old global model), K (# activated
clients).
Output: L_mut (list of mutated models).

1:  g_glb <- w_glb - w_glb'
2:  L_mut <- []
3:  if K mod 2 = 1 then
4:    L_mut <- L_mut + [w_glb]
5:  end if
6:  L <- number of layers of w_glb
7:  Lv_1, Lv_2, ..., Lv_L <- [ -1,-1,...,-1 (floor(K/2) times), 1,1,...,1 (floor(K/2) times) ]
8:  for i = 1, ..., L do
9:    Lv_i <- Randomly shuffle the elements in Lv_i
10:   [v_i^1, v_i^2, ..., v_i^(2*floor(K/2))] <- Lv_i
11: end for
12: for i = 1, ..., 2*floor(K/2) do
13:   w_mut <- w_glb
14:   for j = 1, ..., L do
15:     w_mut.layer_j <- w_glb.layer_j + alpha * v_j^i * g_glb.lg_j
16:   end for
17:   L_mut <- L_mut + [w_mut]
18: end for
19: return L_mut

Mechanism in words: for EACH layer independently, build a list of exactly
2*floor(K/2) sign values, half -1 half +1, then shuffle it randomly; the i-th
shuffled entry becomes that layer's mutation sign for the i-th mutated model.
This per-layer independent shuffle is what produces the "mutation_signs"
structure — each mutated model gets an independently-random pattern of
+1/-1 across layers, but across the K mutated models (for any fixed layer),
the signs are always exactly balanced (zero-sum), satisfying Eq. 4.

--- Dynamic Preference Mutation (acceleration/asymmetry schedule) ---
This is the "mut_bound" / "mut_acc_rate" mechanism referenced by the user.
Quoted from the paper (page 12532-12533):

"Typically, since the model is far away from any optimal solution, the
inference capacity of the global model is poor in the early stage of
training. At this stage, our mutation strategy will focus on mutating the
model in the direction of the gradients. In other words, we shift the
neighborhood in the direction of the gradients. Specifically, we set the
mutation value v in {1, -1 + beta_t} rather than {1, -1}, where beta_t is a
hyperparameter whose value will increase with the number of training
rounds."

(Note: OCR renders this with some garbling — the printed set is {1, -1+beta_t}
based on surrounding text; beta_t effectively biases the "-1" mutation
direction so it's not a full -1 but a partial step, shrinking the asymmetry
between the + and - mutation directions as training proceeds, which has the
effect of pushing mutated models preferentially along the positive-gradient
direction early on, accelerating convergence.)

The schedule for beta_t (Eq. 5):

    beta_t = max( beta_0 * (1 - t / T_b), 0 )                            (Eq. 5)

where T_b is "the bound of the early training stage" — this IS the
"mut_bound" parameter referenced by the user (called T_b / "Tb" in the paper,
not literally named "mut_bound" in the text, but functionally identical: it
is the round-count over which the asymmetric/accelerated mutation decays to
zero, i.e. once t >= T_b, beta_t = 0 and mutation reverts to the symmetric
{1,-1} sign scheme of Eq. 2/Algorithm 2). beta_0 is the INITIAL value of this
decaying bias — this is the "mut_acc_rate" parameter referenced by the user
(called beta_0 in the paper). As t increases from 0 to T_b, beta_t decays
linearly from beta_0 down to 0.

The paper's ablation section explicitly confirms beta_0 values used per
model (see Section 4): "We set beta_0 = 0.3 for CNN and VGG-16, and
beta_0 = 0.5 for ResNet-18." This directly matches the user's stated
"mut_acc_rate 0.3 for CNN/VGG (0.5 for ResNet-18)" — just under the paper's
own symbol beta_0 rather than the literal string "mut_acc_rate" (that name is
presumably from the official code's variable naming, not the paper's
notation).

T_b (mut_bound) itself: the paper's main Settings/Experiments section does
NOT explicitly state a numeric value for T_b in the main text. It is used
symbolically in Eq. 5 and discussed qualitatively in the ablation (Fig. 6b),
but no explicit "T_b = 50" (or any other number) statement was found anywhere
in the paper body. The user's claim of "mut_bound 50" could NOT be verified
from the paper text — it is presumably from the official code defaults
(github.com/HMHelloWorld/FedMut), which this PDF-only extraction has no way
to confirm. FLAGGING AS UNVERIFIED.

--- Convergence Analysis (brief) ---
Theorem 1 states FedMut's convergence rate is of the same order as FedAvg's
(per Li et al. 2019 analysis), under four standard assumptions (L-smoothness,
mu-strong-convexity, bounded stochastic-gradient variance sigma_i^2, bounded
expected squared gradient norm G^2). The bound includes an alpha^2 term
(from Eq. 6, ||w_mut_i,n - w_glb^n||^2 = alpha^2 * ||w_glb^n - w_glb^(n-1)||^2)
inside the constant B = (1/K^2) sum sigma_i^2 + 6*L*Gamma + (16+32*alpha^2)*(E-1)^2*G^2,
showing the mutation magnitude alpha enters the convergence bound but does not
change its asymptotic order. Full derivation/proof is referenced as being in
an Appendix NOT included in this PDF (see note in Section 1).

FedAvg vs ~18 for FedMut, though these are landscape-plot magnitudes, not
accuracy or loss-value comparisons to be read as absolute test-loss numbers).

--- 4.8 Convergence curves (Figure 5) ---
Learning curves (accuracy % vs round, 0-1000) for CIFAR-10 + ResNet-18, all
four heterogeneity settings (d=0.1, d=0.5, d=1.0, IID), comparing FedMut vs
the four baselines. Qualitative findings stated in text: "FedMut approach can
converge more quickly than all the four baselines... FedMut can achieve
higher accuracy than all the four baselines in almost all the FL rounds...
as the level of non-IID increases, the magnitude of the learning curve rises
and the number of rounds needed for convergence increases." (Note: "the
magnitude of the learning curve rises" likely a wording artifact — probably
means variance/fluctuation of the curve increases with higher non-IID
severity, based on the visibly noisier d=0.1 subplot.)

--- 5.1 Ablation: Mutation range alpha (Figure 6a) ---
Tested alpha in {1, 2, 3, 4, 5} (denoted "FedMut-1" through "FedMut-5" in the
figure legend), compared against FedAvg (= FedMut with alpha=0), on CIFAR-10
with ResNet-18 presumably (same setup as Fig 5, though the exact
dataset/model/heterogeneity condition for Fig 6 is not explicitly restated in
the ablation paragraph — it is reasonable to infer it's the same CIFAR-10/
ResNet-18 setup used throughout the convergence-curve figures, but the paper
does not explicitly re-state this for Figure 6).
Findings: "when alpha < 5, the inference accuracy of FedMut increases with
increasing value of alpha" (so accuracy generally improves from alpha=1 up to
alpha=4) "because a larger value of alpha can guide FL to converge in a
flatter area." But "when alpha = 5, FedMut cannot train a usable model... a
too-large mutation range may cause training to be unable to find a flat
enough area, which results in failed convergence." This directly supports
why the main results table uses alpha=4.0 (apparently near the top of the
usable range, just below the alpha=5 failure point).

--- 5.2 Ablation: Dynamic preference mutation beta_0 (Figure 6b) ---
Tested beta_0 in {0.0, 0.1, 0.3, 0.5, 0.7} (denoted "FedMut-0.0" through
"FedMut-0.7"), compared against FedAvg.
Findings: "the higher value of beta [beta_0], the faster the training
converges... a too large value of beta may cause training to fail." (Same
style of failure mode as alpha — there's a sweet spot, and going too far
causes outright convergence failure rather than merely worse results.) This
is consistent with the main-results choice of beta_0=0.3 (CNN/VGG) and 0.5
(ResNet-18) — these fall within the tested, apparently-safe range from the
ablation (0.1-0.5), not at the extreme (0.7).

--- 5.3 Privacy / secure-aggregation compatibility ---
"Similar to the traditional FedAvg, the mutation strategy in FedMut is based
on the aggregated global model rather than local models. Therefore, our
FedMut approach can directly use the secure aggregation mechanism.
Consequently, in FedMut, the cloud server cannot obtain raw data or the local
model of clients." — i.e. because mutation operates purely on the already-
aggregated global model (server-side, post-aggregation), it doesn't require
the server to see any individual client's uploaded model in the clear, so it
composes with secure aggregation protocols (unlike, e.g., device-grouping
methods that need per-client model access).

--- 5.4 Communication overhead ---
"Same as FedAvg, the communication overhead of FedMut only includes K models
for dispatching and K models for uploading in each FL round. Therefore,
FedMut is without any additional communication overhead compared to FedAvg."
I.e., despite generating K distinct mutated models server-side, this doesn't
increase the number of model transmissions versus vanilla FedAvg (still
exactly K dispatches + K uploads per round) — the mutation computation itself
is a server-side cost only, not a communication cost.

--- 5.5 Compute cost discussion ---
No explicit wall-clock, FLOPs, or training-time comparison numbers between
FedMut and FedAvg are given anywhere in the paper. The only compute-related
detail stated is the hardware used for all experiments (Ubuntu workstation,
Intel i9 CPU, 64GB RAM, 2x NVIDIA RTX 4090 GPUs — see Section 4.1). No
per-round or per-experiment runtime, nor any statement that FedMut's mutation
step adds negligible/non-negligible server-side compute overhead, appears in
the paper text.
